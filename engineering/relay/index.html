設計検証制作の進め方

RELAY / BACKEND · QUALITY · WORKFLOW

保存できる、その先の
「困ったとき」まで考える。

業務依頼を作成し、状態を変え、経緯を残す。その小さな流れの中で、他人のデータ、通信の再送、同時更新をどう扱うか。Relayの裏側を、設計と検証から紹介します。

01 / THE PROBLEM

依頼と、その理由を残したい。

想定する困りごと

Web改修や集計作業の依頼が、会話の中に埋もれてしまう。何を頼まれたか、今どこまで進んだか、いつ状態が変わったかを一か所で確認したい。

今回の完成条件

  • 本人の依頼を保存・検索・更新できる。
  • 再送による二重登録を防ぎ、古い状態で上書きしない。
  • 変更と履歴の片方だけが保存されないようにする。

架空業務を題材にした本人専用のデモです。実企業への導入実績、複数人のチーム共有や管理者権限を提供する製品ではありません。

02 / BOUNDARIES & DATA

画面を信用するのではなく、サーバーで確かめる。

  1. ブラウザ件名・分類・優先度や、読み取り時のversionを送る。所有者は送信させない。
  2. ChatGPT認証ホストから得た認証済みIDを使う。メールアドレスを保存キーにしない。
  3. APIログイン・入力・Originを確認。所有者条件を含むSQLを実行する。
  4. D1 / SQLite重複制約と条件付き更新。トリガーで変更履歴も一緒に記録する。

データの関係

requests / 依頼

  • id / owner_id
  • title / description / category / priority
  • status / version
  • idempotency_key / payload_hash
1つの依頼
1 → N
作成・状態変更の履歴

request_events / 履歴

  • id / request_id
  • action
  • from_status / to_status
  • created_at

所有者ID、送信キー、本文ハッシュはAPIの返却項目から除外しています。履歴は経緯の確認用で、改ざん耐性を持つ商用監査ログではありません。

03 / API CONTRACT

APIと、失敗したときの返し方。

操作契約主な境界
GET /api/requests本人の依頼を状態・キーワードで検索未認証は401。他人の依頼は含めない。
POST /api/requests送信キーと本文を照合して作成初回201。同内容の再送200。キーの内容違い409。
PATCH /api/requests/:id読み取り時のversionを照合して更新古いversionは409。他人・不存在IDは共に404。
GET /api/requests/:id/events本人の依頼の変更履歴を取得依頼の所有者を確認。未認証401、権限外404。

04 / EVIDENCE, NOT A BADGE

成功する操作だけでなく、失敗を確かめる。

確かめる状況期待する動作検証方法
別の所有者の依頼が実在する一覧・検索・履歴に出ず、更新しても元データが変わらない。ローカルSQLiteに架空の利用者A/Bを用意し、本番と共有するSQLで検証。
同じキーで作成を再送する依頼と作成履歴が増えない。同じ所有者・送信キーのINSERT結果と件数を照合。
古いversionで状態を変更する最新の状態や履歴を上書きしない。先の更新後、元のversionで更新を試みて不変を確認。
履歴の保存が失敗する依頼の作成・更新も取り消され、不整合を残さない。隔離したSQLiteに失敗用トリガーを置き、ロールバックを確認。

保存済みの検証結果

テストを実行して生成した結果を読み込みます。このページを開いても、本番データへの試験は実行しません。

実行条件と検証対象

    本番・ローカル・説明用デモを区別しています。

    公開版は1アカウントで保存・状態変更・履歴・再ログイン後の表示を確認済みです。別所有者の境界や履歴保存失敗は、架空データを使うローカル試験です。上の件数にはHTTP試験や画面操作の件数を含めていません。

    Relay画面の「入力・リクエスト検証」は固定入力を共通バリデーターへ渡す別のデモです。認証の突破や第三者への攻撃を行うものではありません。

    05 / HOW WE BUILT IT

    AIと進めたこと、自分で確かめること。

    人が決める側

    どんな仕事を扱うか、何を見せたいか、操作して違和感がないか。課題の選択、要望、公開範囲、改善の方向を坂本陽介が確認しながら進めています。

    AIの支援を使う側

    設計の候補、実装、テストの作成と実行、問題の切り分けにAIエージェントを利用しています。AIの支援を受けた範囲と、作品で確認できることを分けて説明します。

    今回の改善では、画面から分かりにくかったデータの境界を整理し、一覧・検索・履歴にも所有者条件が働くことを検証しました。これは個人制作での開発・検証記録であり、顧客向け運用やチーム実務の実績とは区別しています。

    06 / WHAT IS NOT INCLUDED

    できることと、まだ扱っていないこと。

    この作品で確認できる範囲

    • API・DB・画面をつないだ本人専用の依頼管理
    • データの所有者境界、再送・競合・履歴の整合性
    • 入力検証、テストと改善の記録

    今後、用途に応じて設計する範囲

    • チーム共有、役割別権限、担当者・通知・削除
    • レート制限、負荷試験、監視・バックアップ復旧
    • 第三者診断と実顧客を対象にした運用

    1人30件・1依頼50回の状態変更上限を設けたデモです。実在の個人情報・社内情報は入力しないでください。コード原本は非公開を維持し、ここでは設計説明と匿名化した検証結果だけを公開しています。
